# Stroom LLM 账号接入与模型组路由计划

- 状态：计划稿，尚未实现
- 更新日期：2026-10-10
- 上游能力参考：CLIProxyAPI 官方仓库，main 快照 d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5

## 1. 目标与范围

把 Stroom 现有的 LLM 供应商配置升级为本地账号与模型组管理，让 Stroom 能直接使用用户已有的 API Key、自定义端点、官方 OAuth、CLI 或订阅账号，并在等价模型之间按简单策略选账号、限额和故障回退。

这是 Stroom 的个人本地功能，不建设多租户服务、公开代理网关、计费或面向转售的管理系统。也不实现通用的 OpenAI、Anthropic、Gemini 等客户端协议转换网关。Stroom 需要为每类上游实现其自身的认证与请求适配，并将返回结果接到 Stroom 内部聊天接口。

CLIProxyAPI 是已选定的上游账号能力基准。按其官方仓库中的全部一等认证/账号连接器与上游接入能力建立迁移清单；不是按其 README 中赞助商、周边管理面板或第三方客户端列表来扩张 Stroom 功能。

## 2. 配置页与运行时调用的关系

LLM 管理页面负责编辑和保存账号、模型、模型组与路由策略。它本身不是发出聊天请求的运行时入口。

当前 Stroom 的供应商配置保存在 provider entries 中。普通对话会由 ChatAdapter 解析配置并构建 ChatService；标题生成、上下文压缩等内部任务也有经 ChatAdapter 创建的一次性 ChatService 的路径。当前搜索到的 createChatProviderFromConfig 五个调用点都在 lib/services/chat_adapter.dart，工厂定义在 lib/providers/chat_api_provider.dart。

因此，账号选择和路由策略应进入共享的运行时服务边界，由 ChatAdapter 解析模型/模型组、选择账号，再构造对应的上游客户端；设置页面只负责编辑配置，不在页面控件中实施路由。第一阶段还要盘点应用内其他直接调用模型 API 的路径，确认它们是否属于本次 LLM 账号路由范围，并将共用 LLM 路由的调用收敛到同一个入口。OCR、ASR、TTS、MCP 等其他能力仍由各自的服务负责。

## 3. CLIProxyAPI 上游支持基准

实现前应在清单中冻结所选 CLIProxyAPI 快照的全部核心认证和上游连接器，并逐项对应 Stroom 的登录、凭据保存、续期、模型发现、请求与可用额度能力。当前官方 README 明确列出的核心来源至少包括：

| --- | --- |
| OpenAI Codex | ChatGPT/Codex OAuth，多账号 |
| Anthropic Claude Code | OAuth，多账号 |
| Google Gemini CLI | Google CLI 账号认证 |
| Google Antigravity | Google 账号认证 |
| Google Gemini API / Generative Language | API Key |
| Google AI Studio Build | 多账号接入与负载分配 |
| Google Vertex AI | 云端凭据接入 |
| xAI Grok Build | OAuth，多账号 |

这张表是公开文档中的初始清单，不代替代码核对。实现前需要检查参考快照的 README、核心 auth/connectors 目录和配置文档，把代码实际支持但 README 未列出的核心连接器补入同一验收矩阵。各渠道的模型、认证限制和额度接口可能变化，清单应注明验证过的上游快照。

Copilot、Kiro、Cursor 等若只出现在 CLIProxyAPI 的第三方客户端或周边项目列表中，不应据此当作 CLIProxyAPI 核心上游账号连接器；只有所选快照的核心代码确有对应账号认证连接器时，才纳入“完整迁移”清单。GLM、DeepSeek 等可通过 API Key/兼容端点接入；它们的网页登录或订阅账号则只有在基准代码中存在一等连接器时才计入该清单。

## 4. 建议的数据模型

把供应商、认证账号、上游模型和 Stroom 可选模型组分开建模，避免当前“一个供应商配置包含一个密钥和多个模型”的结构继续承载所有职责：

- **上游连接器**：声明供应商的认证方法、请求能力、支持的模型功能、账号状态/额度查询能力，以及如何创建原生上游客户端。
- **认证账号**：一个可独立登录、刷新、停用和限额的 API Key 或 OAuth/CLI/订阅凭据；包含连接器类型、凭据引用、端点、账号备注、状态、配额信息和策略。
- **上游模型映射**：账号实际可调用的模型 ID 与能力；例如工具调用、视觉、流式输出、上下文长度等。仅呈现连接器已验证支持的能力。
- **模型组**：Stroom 面向助手/对话暴露的稳定模型身份，包含一个或多个兼容上游模型/账号及其优先级。允许同一供应商的多个认证账号，也允许多个供应商参与同一等价模型组。
- **路由运行状态**：本地用量计数、限额窗口、冷却时间、最近错误和并发占用。账号启停或额度重置不应更改历史会话中的模型身份。

凭据不应随模型组重复存储。数据模型只保存安全凭据库中的引用；日志和导出文件不得包含 access token、refresh token、API Key 或完整授权响应。

## 5. 路由规则

一次请求按以下顺序选择候选账号：

1. 按稳定模型组 ID 解析请求；旧会话和内部任务仍须能解析它原先保存的模型引用。
2. 过滤掉未启用、认证失效、暂处冷却、模型/功能不匹配、超并发、触及使用上限或低于保留额度下限的候选账号。
3. 先尝试当前最高优先级层；该层没有可用账号时，才进入下一优先级层。
4. 同层默认采用“最少使用”策略；可选轮询，或按余额策略选择账号：优先使用余额较多的账号以分散消耗，或优先消耗余额较少但仍高于保留线的账号。余额策略只影响同一优先级内的排序，选择结果和跳过原因应能在账号页查看。
5. 回退范围是模型组内策略：可设置为仅在同一上游供应商的多个账号间切换，或允许在当前模型组配置的其他供应商间切换。不得静默跳到模型组以外的模型。

仅对可恢复的错误尝试下一个候选账号，例如认证被拒、限流/额度耗尽、连接失败或可重试的上游 5xx。遵守上游给出的 Retry-After/重置时间并设置冷却。明显由请求内容造成的参数错误不应通过重复切换账号掩盖。流式响应已经向界面输出内容、工具调用已发出或请求有副作用后，不自动重放整次请求，以免重复输出或重复执行。

切换账号时应维持用户请求的模型组身份和请求能力。如果候选供应商对工具、视觉或其他参数的支持不等价，就应跳过该候选并说明原因，而不是静默降级。

## 6. 额度、使用上限和并发

账号级规则为核心；模型组可选设置汇总上限和并发上限，防止组内账号合计用量超出个人预算。汇总额度只在成员计量单位可比时启用，不把不同厂商的额度单位、token 和请求数直接相加。

- 每个账号和模型组支持五小时、日、周、月四种窗口。
- 每个窗口可选滚动窗口或日历窗口；默认滚动。日历窗口按用户配置的本地时区计算。
- 同时支持“剩余额度保留下限”和“使用量上限”。下限用于保留订阅额度，上限用于控制个人用量；两者可独立设置，不能以设置其中一个替代另一个。
- 下限/上限都可按固定数量或已知总额度的百分比设置。百分比没有可靠总额度时显示为未解析并要求用户改用固定值或补充额度基准，不能猜测。
- 并发数在账号和可选模型组层面限制；路由前原子占用，成功、错误、超时或取消后释放。
- 优先使用上游实际报告的额度、重置时间和用量。API 响应没有这些字段时，仅累计实际收到的请求数、输入/输出 token 等可观察指标；价格/成本估算不作为阻断依据，除非未来另行明确要求。
- 对上游无额度查询接口的 API Key 账号，允许用户输入初始额度/预算基准；未知余额保持“未知”，不把未知误认为充足。

窗口使用来源、单位、同步时间、当前已用、剩余量和重置时间都要可见。账号认证可用但额度未知时，用户仍能用固定上限和并发规则管理它。

## 7. 认证、存储和旧数据迁移

各连接器直接处理其上游认证流程，包括授权开始、回调/设备码完成、刷新、登出、凭据有效性和重新授权。API Key、自定义 URL 和 OAuth/CLI 账号都作为一等账号类型管理。

凭据使用 Stroom 的平台安全存储抽象保存，配置 JSON 中留凭据引用；实现阶段需核对桌面、移动端和 Web 平台的可用安全能力，并明确不支持的存储环境行为。禁止在诊断日志中输出秘密。OAuth 回调、令牌刷新失败和用户主动断开应有可理解的状态。

迁移当前 provider_entries / ProviderConfigItem 配置时：

1. 每条旧 LLM 配置迁移为一个认证账号及其原有上游模型映射。
2. 为旧模型创建或映射到默认模型组；只有一个账号时，路由结果应与迁移前一致。
3. 保留旧配置 ID、模型 ID 和已有助手/会话/系统任务的引用映射，不重写聊天历史。
4. 迁移采用可重试、可校验、有备份的方式；全部新结构落盘并通过校验后才标记完成。升级失败时保留原配置，提供回滚或修复路径。
5. 在完整矩阵和迁移验证前，不删除旧字段的读取兼容。

## 8. 管理页面的最小范围

以个人使用为目标，页面围绕“账号”和“模型组”提供必要操作：

- 添加账号：API Key/自定义端点或连接器原生登录；显示账号状态和最后验证时间。
- 查看/编辑该账号可用模型、优先级、备用范围、限额窗口、余额保留、使用上限和并发数。
- 查看模型组成员、默认模型、当前优先级、组级策略和可用状态。
- 展示上游已报告的五小时/日/周/月额度与重置时间、本地实际用量、保留量、并发占用和近期失败原因。
- 支持用户手动检查连接、刷新账号状态、重新授权、禁用账号和调整排序。

不做面向中转站的客户 Key 管理、租户权限、价格表、计费面板、请求公开分享或运营级分析后台。

## 9. 实施阶段

### 阶段 0：清点调用和冻结上游矩阵

- 审计所有 LLM 出站请求，确认普通对话、标题生成、上下文压缩、任务流和助手工具各自的调用路径。
- 冻结 CLIProxyAPI 的参考提交和完整核心认证/账号连接器矩阵；分清 OAuth/CLI 账号、API Key、自定义兼容端点和第三方客户端集成。
- 为每个矩阵项记录登录、令牌生命周期、模型发现、上游请求、用量/额度查询、支持能力和可验证环境。

**完成标准：** 每个 LLM 请求入口和每个上游连接器都有归属与验收条目；不再以模糊的“兼容各种格式”作为范围。

### 阶段 1：账号与模型组数据结构及迁移

- 定义账号、模型组、成员优先级、凭据引用、配额/并发策略和用量记录。
- 实现旧 provider_entries 到新结构的可重复迁移、校验、备份和引用映射。

**完成标准：** 现有配置升级后能正常请求；会话和助手仍指向原模型；迁移可重入且不会丢失 API Key 或模型映射。

### 阶段 2：连接器基础设施与认证存储

- 实现连接器注册、统一状态/能力描述、凭据安全存储和账号生命周期。
- 逐个实现冻结清单中的认证连接器与上游原生请求客户端。
- 为账号提供连接测试、模型发现及可用时的额度/重置时间读取。

**完成标准：** 矩阵中的每项都有对应实现和逐项验证记录；未知或不支持能力明确显示，不伪报支持。

### 阶段 3：用量、限额和模型组路由

- 实现请求前资格判断、优先级、同层策略、余额上下限、五小时/日/周/月窗口与并发占用。
- 实现同供应商账号池/整个模型组的 fallback 策略、错误分类、冷却与可解释的路由记录。
- 增加防止流式响应或工具调用重复执行的保护。

**完成标准：** 路由行为可按确定性用例验证；每个账号为何被选中或跳过均可追溯。

### 阶段 4：ChatAdapter 集成与页面替换

- 将共享的模型解析与账号选择接入 ChatAdapter/ChatService 创建和请求执行路径。
- 覆盖普通对话以及使用同一共享入口的标题、压缩、任务流和助手调用。
- 用账号和模型组管理替换当前 LLM 供应商页的核心表单，保持必要诊断可见。

**完成标准：** 所有纳入范围的 LLM 出站路径使用相同账号、限额和 fallback 逻辑；其他功能服务不被误改。

### 阶段 5：回归与发布准备

- 运行旧数据迁移、各连接器登录/刷新、路由策略、额度窗口、并发和取消/重试回归。
- 检查凭据存储/导出/日志边界及桌面、移动端、Web 的实际支持。
- 补齐用户文档和每个上游连接器的限制说明。

**完成标准：** 现有 API Key 用户无须手工重建所有配置；完整核心连接器矩阵逐项验收；失败迁移可恢复；请求不会因 fallback 重复执行已输出内容或工具副作用。

## 10. 实施验收用例

至少覆盖以下行为：

1. 单账号模型组与迁移前一致；旧对话、助手和系统任务的模型引用仍有效。
2. 同供应商两个账号按优先级工作；当前优先级账号触及限额后切到同层可用账号，再在整层耗尽后进入下一层。
3. 组内两个供应商可按设置参与 fallback；切换范围设为同供应商时不跨供应商。
4. 余额固定下限、百分比下限、使用固定上限、百分比上限独立生效；上限/下限同时设置时执行更严格的可用条件。
5. 五小时、日、周、月滚动与日历窗口边界、重置时间和时区计算正确。
6. 并发达到上限时不再分配新请求；成功、异常、超时和取消都会释放占用。
7. 超时、限流、认证失败、上游 5xx 等按策略回退；无效请求不无意义地遍历账号。
8. 流式输出开始后、工具副作用发出后不重放；取消会释放流和并发占用。
9. 额度未知、刷新失败或模型能力不匹配时，界面与路由原因保持诚实且可诊断。
10. 矩阵中的每个上游账号连接器都完成真实登录/凭据、刷新、模型发现、请求调用和支持能力验证；测试不得只验证“可以保存账号”。
