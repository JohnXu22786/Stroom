# Stroom 分支与版本管理约定

本约定适用于本仓库所有维护者和贡献者。Git 和 GitHub 没有规定唯一的分支命名或开发流程；常见做法包括以 `main` 配合短期功能分支，或采用 Git Flow 一类带长期开发线和发布线的流程。本仓库选择用 `v<MAJOR>.<MINOR>` 表示版本开发线。这个名称是本仓库的约定，不是通用标准。

下文尖括号中的内容都是占位符，需在实际创建分支或标签时替换；列出一种命名形式不代表对应分支已经存在。只创建当前开发和维护所需的分支，不提前登记未启动的版本线。

## 1. 分支类型

| 分支形式 | 用途 | 生命周期 |
| --- | --- | --- |
| `main` | 默认分支和当前主线，承载当前稳定版本及日常维护。 | 长期 |
| `v<MAJOR>.<MINOR>` | 对应次版本系列的开发与集成分支。 | 开发该版本系列期间 |
| `release/<MAJOR>.<MINOR>` | 主线交接后，继续维护仍受支持的旧版本系列；只在确有维护需要时创建。 | 该系列停止维护时结束 |
| `feat/<topic>` | 功能开发工作分支。 | 短期，合入目标分支后删除 |
| `fix/<topic>` | 缺陷修复工作分支。 | 短期，合入目标分支后删除 |
| `docs/<topic>` | 文档修改工作分支。 | 短期，合入目标分支后删除 |
| `ci/<topic>` | CI 或构建配置修改工作分支。 | 短期，合入目标分支后删除 |

工作分支名称使用小写、简短主题和连字符；主题应说明改动内容。若仓库另有约定的工作类型前缀，可在此表中增补。

## 2. 开发与修复规则

- 每项开发或修复从实际目标版本分支创建独立工作分支。开发线启动时，从已确认的集成基点创建 `v<MAJOR>.<MINOR>`；不要为了占位提前创建未来版本分支。
- PR 必须以实际目标分支为 Base，并说明目标版本系列。不得把工作分支直接提交到 `main`、版本开发分支或维护分支。
- 适用于旧版本的修复，先进入对应目标分支；如较新的开发线也需要该修复，再通过单独 PR 向前同步。不自动反向同步。
- 较新版本专属功能不得合入旧版本分支。不同版本间不兼容的修复应分别适配，并在各自目标分支验证。
- 长期分支间的必要同步通过 PR 进行，评审冲突并确认变更方向；定期同步，避免在交接前积累大量差异。
- 共享分支通过 PR、评审和目标分支要求的 CI 检查后合并。不得未经安排跨版本合并或强制更新共享分支。

## 3. 版本主线交接

当某条 `v<MAJOR>.<MINOR>` 开发线准备接管 `main` 时：

1. 确认交接范围及基点，并完成 `main` 到该开发线的最后一次必要同步。
2. 若原版本系列仍需维护，在主线切换前，从当前 `main` 创建相应的 `release/<MAJOR>.<MINOR>`；若无需继续维护，则不创建。
3. 完成目标分支要求的评审、CI 和合并验证。
4. 通过 PR 将准备接管主线的版本开发分支合入 `main`。
5. 合入后，`main` 承载新的主线；如已创建维护分支，则由该分支继续承载旧版本的必要修复。

每次交接都按当时实际存在且已确认的分支执行，不预设后续版本或维护分支。

## 4. 版本标签

发布标签使用 `v` 前缀，格式为 `v<MAJOR>.<MINOR>.<PATCH>`。`v` 是标签命名约定，不属于 SemVer 版本号本身；去掉前缀后的版本号遵循语义化版本（SemVer）。预发布标签可在版本号后添加 SemVer 允许的预发布标识。标签表示一次具体发布；版本开发分支表示持续变化的代码线，两者用途不同。

## 5. GitHub 仓库设置

- 默认分支保持为 `main`。
- 对 `main`、版本开发分支和维护分支配置适当的保护规则，例如要求 PR、评审和 CI 检查。
- PR 说明目标分支、目标版本系列及变更目的；合并前满足目标分支的保护规则。
- 跨版本同步应在 PR 中说明来源、目标和适用范围。
- 仓库版本策略改变时，同步更新本约定。
