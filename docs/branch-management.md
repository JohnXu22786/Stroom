# Stroom 分支与版本管理规范

## 1. 分支职责

| 分支 | 版本系列 | 用途 |
| --- | --- | --- |
| `main` | 当前主线；规划为 0.5.x | 维护当前主要版本，包括任务流系统；承载正常修复、发布和维护。 |
| `v0.6` | 0.6.x | 下一阶段功能开发与验证，任务以 `v0.6.0` Milestone 为准。 |
| `v1.0` | 1.0.x | 长期规划的重大功能及架构调整，任务以 `v1.0.0` Milestone 为准。 |
| `release/0.5` | 0.5.x | 0.6.x 接管 `main` 后继续维护 0.5.x。 |
| `release/0.6` | 0.6.x | 1.0.x 接管 `main` 后继续维护 0.6.x。 |

`release/0.5` 和 `release/0.6` 按主线交接时的实际需要创建，不要求提前存在。

### 本次任务的临时集成分支

本次 DSH 对话页面迁移使用 `v0.7` 作为跨平台集成目标。`v0.7` 是该任务的临时目标分支，不纳入上表的长期版本线；此任务通过 PR 合入 `v0.7`，`v0.7` 是否及何时合入 `main` 按版本交接规则另行决定。

## 2. 开发规则

- 每项功能或修复都从其目标版本分支创建独立工作分支；分支名使用类型前缀和简短主题，例如 `feat/<主题>`、`fix/<主题>`、`docs/<主题>`、`ci/<主题>`。
- PR 的 Base 必须是目标版本对应的分支，并在 PR 中说明目标版本。不得直接向 `main`、`v*` 或 `release/*` 提交。
- 低版本的必要修复可以通过单独 PR 同步到高版本；不自动反向同步。高版本专属功能不得提前合入低版本。
- 对不同版本不兼容的修复，应在目标版本单独适配，并分别验证。
- 长期开发分支定期通过 PR 从低版本分支同步必要且兼容的修复；维护分支不从高版本分支同步。每次同步都应遵守低版本回补和高版本专属功能不得下沉的规则，避免在版本交接前集中产生大量冲突。
- 通过目标分支要求的评审和 CI 后再合并；禁止未经安排的跨版本合并和强制更新远端分支。

### 开发分支的创建

- 开始 0.6.x 开发时，从当时的 `main` 创建 `v0.6`。
- 0.6.x 接管 `main`、开始 1.0.x 开发时，从当时的 `main` 创建 `v1.0`。
- 维护分支只在主线交接时按第 4 节创建；功能和修复工作分支仍从其目标版本分支创建。

## 3. 版本开发范围

### 0.5.x

维护当前版本的完整功能，包括任务流系统。主要进行 Bug 修复、兼容性和稳定性改进。

### 0.6.x

开发下一阶段规划的功能，详细任务以 `v0.6.0` Milestone 为准。

### 1.0.x

开发长期规划的重大功能及架构调整，详细任务以 `v1.0.0` Milestone 为准。

## 4. 主分支交接

### 0.6 接管 `main`

1. 从当前 0.5 主线创建 `release/0.5`。
2. 完成 `main` 向 `v0.6` 的最后一次同步。
3. 完成合并验证后，通过 PR 将 `v0.6` 合入 `main`。
4. `main` 开始维护 0.6.x，`release/0.5` 继续维护 0.5.x。

### 1.0 接管 `main`

采取相同流程：先从当前 0.6 主线创建 `release/0.6`，同步 `main` 到 `v1.0` 并完成合并验证，再通过 PR 将 `v1.0` 合入 `main`。之后 `main` 维护 1.0.x，`release/0.6` 继续维护 0.6.x。

## 5. GitHub 规则

- 默认分支保持 `main`。
- 每个 PR 必须明确目标分支和目标版本，并通过目标分支要求的 CI 检查。
- 禁止未经安排的跨版本代码合并；必要回补按开发规则单独提交和验证。
- 版本标签统一使用标准 SemVer 格式。
- 本规范随主线版本交接更新。
