Date: 2026-11-06. Final Stroom audit base: `733aa2e39c00ad36f7b6095c530c48c34033282f` (`origin/v0.6`, after M63–M69). ## Source-backed gaps resolved after the initial M62 base

### OneMinAI (`oneminai`) — M64, PR #1498

The pinned source `open-sse/config/providers/registry/oneminai/index.ts:3-28` and `open-sse/executors/oneminai.ts:46,358,368` uses `promptObject.prompt`, event-framed SSE, and `API-KEY` authentication. Current Stroom has a named `oneminai` account and `oneminai.chat` adapter (`lib/services/oneminai_protocol.dart`, `api_protocol_config.dart`, `llm_connector_service.dart`, and `llm_routed_chat_provider.dart`). The adapter sends the native request shape and translates streaming/nonstreaming replies through the shared Chat and Task Flow route. It explicitly rejects unsupported tools, formats, and media.

### Routeway (`routeway`) — M63, PR #1489

The pinned source `open-sse/config/providers/registry/routeway/index.ts:4-18` declares OpenAI Chat Completions and requires `User-Agent: Mozilla/5.0 OmniRoute/1.0`. Current Stroom includes a Routeway provider preset with the matching Chat Completions endpoint, `/v1/models` discovery, passthrough model IDs, and the static header applied to inference and discovery requests (`lib/services/llm_provider_preset_catalog.dart`). It routes through shared Chat and Task Flow.

Both routes are merged into `v0.6`; neither requires a remaining implementation unit. Their API catalog rows are counted under “Named routes added after the initial M62 base” above. This audit makes no live credential or upstream request claim.

## Registered-account route admission — M68 complete

M68 reconciled registered connector/auth modes with the protocol choices that the model-group selector and Chat/Task Flow runtime admit. It added only request paths supported by the existing connector implementation and its tests, plus Antigravity's distinct native `google.antigravity.generate_content` protocol. Authentication remains independent of protocol selection; unsupported provider/protocol combinations remain unavailable by design and are rejected during configuration/preflight.

`llm_routed_chat_provider_test.dart` checks the audited account/protocol pairs against `supportedApiProtocolsForSupplier`, including negative cases for unsupported GitLab Duo formats. `api_protocol_config_test.dart` checks supplier defaults and supported protocol choices. M68 merged as PR #1524 before this audit base. This closes the registered-account selection gap found during M62; it does not claim feature parity for every optional upstream field or entitlement.

## Zed IDE keychain import — M69 complete

M69 implements the pinned source's Zed IDE credential import on macOS, Linux, and Windows. It discovers supported vendor credentials locally, lets the user choose which account to add, re-reads the native keychain item and checks its fingerprint, then stores the credential in Stroom's secure store under the original OpenAI, Anthropic, Google, Mistral, or xAI account type. On macOS, Stroom explains that discovery may trigger OS Keychain permission prompts; a denied item is skipped. Credential values are not sent to Zed or displayed in the import UI. The imported vendor account then uses that vendor's normal protocol and Chat/Task Flow route. This is separate from the `zed-hosted` OAuth account and does not make Zed itself a vendor connector. M69 merged as PR #1526.

## No-auth and CLI-owned source modes

The pinned OmniRoute no-auth catalog, registry, and executor paths include the CLI-owned conversational modes `auggie`, `codex-app-server`, and `zcode`. These three modes are listed separately from the 234 API-key rows and are implemented as local CLI-owned accounts in M65–M67. The local-provider catalog separately includes Devin CLI Agentic Bridge, which has its own `devin-cli-agentic` account and ACP route; see the connector matrix. Stroom delegates login/session ownership to the official local app/CLI and does not import its credential file. They are separate from Stroom’s Codex OAuth route: the Codex App Server uses JSON-RPC/WebSocket, Auggie invokes its CLI, and ZCode uses its app-server protocol. `duckduckgo-web` retains browser cookie/page-session state and challenge handling, so it is explicitly excluded by the approved browser-session boundary. `cloudflare-playground` similarly uses a browser-backed reverse-engineered session route and is outside scope. AI Horde anonymous and optional-priority-key modes and UncloseAI also have named Stroom routes; their protocol and current availability limits are recorded in the connector matrix.

## Current coverage conclusion and limits

At `733aa2e`, every in-scope mode with an executable conversational contract in the three frozen references has a documented Stroom account path and Chat/Task Flow route, including registered connector/protocol admission (M68), local CLI-owned modes (M65–M67), and Zed IDE credential import on macOS, Linux, and Windows (M69). The exact row-level classifications remain in the matrix. This is implementation coverage, not a claim of complete feature parity: provider-specific fields, tools, modalities, streaming behavior, plan entitlements, and model availability remain limited to each implemented adapter and its capability checks.

Eleven API catalog rows have no executable conversational runtime in the frozen references; Stroom does not infer an endpoint, authentication method, or integration for them. This is an evidence boundary, not a claim those providers cannot be integrated if a supported contract is later documented. Browser-session routes, embeddings/rerank, Decision APIs, external Stroom API ingress, multi-user proxy features, and explicitly prohibited third-party OAuth remain excluded. No authentication flow, provider entitlement, or upstream request was validated live. M0 and M11 acceptance snapshots predate the final M63–M69 coverage; this report and the matrix's current-status column are authoritative for final v0.6 account coverage.
