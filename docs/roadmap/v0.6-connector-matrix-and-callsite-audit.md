## Frozen three-project account/API union and Stroom execution mapping

This is the source union, normalized by **service + account/auth mode + upstream API family**. The account-mode execution descriptions in this section reflect the original M0 planning snapshot and are superseded for current status by the M62 audit. The source repositories expose many additional model aliases and endpoints; aliases are not new account connectors. Provider catalog entries are included below only when they execute conversational model turns. Browser cookies/web sessions; public Stroom API ingress; embeddings/rerank; Decision models/APIs; tenant/customer key, quota, billing, or proxy-operator workflows; non-conversational media/tool endpoints; and the Kiro third-party OAuth integration prohibited by its pinned terms are excluded. Images, audio, video, and files carried inside a chat turn remain supported content requirements. The three projects are evidence sources, not implementations Stroom may copy.

The following table preserves the original M0 acceptance plan and its source evidence. Its “Original M0 planned work” column is historical; the “Stroom v0.6 path present” and M62 classification columns have since been reconciled against the final v0.6 implementation. For current coverage, use the M62 audit. At M0, each listed in-scope mode was treated as a required connector execution item: its account/auth state must resolve through the account registry and its model calls must run through the shared `ChatAdapter`/`ChatService` route used by Chat and Task Flow. Credentials that Stroom owns must use secure credential references; CLI-owned sessions remain separately identified account entries whose local bridge follows the source contract without importing the CLI token into Stroom. Anonymous/no-auth entries use the documented request semantics and do not prompt for credentials. Stroom's current generic provider rows or stored legacy labels do not count as an implementation of a reference login flow.

## Stroom LLM call-site audit

The source audit searched production Dart under `lib/` for `ChatAdapter`, `ChatService`, `createChatProviderFromConfig`, `sendPrompt`, stream entry points, LLM endpoint/protocol strings, and HTTP client request calls, then followed each service construction and request path. At the audited base commit, `ChatAdapter` is the shared provider-resolution boundary for chat: it creates per-conversation or transient `ChatService` instances, and `createChatProviderFromConfig` selects the OpenAI-compatible or Anthropic provider. Those providers own the chat HTTP clients. `OcrService` separately sends image content to an OpenAI-compatible Chat Completions endpoint; despite being an OCR feature, that is a direct model request and is inventoried below.

### Explicit exclusions

OCR, ASR, TTS, MCP transport, HTTP tools, web search tools, file upload/download APIs, connectivity probes for MCP/HTTP tools, and other non-LLM service requests are outside this LLM router unless they make an LLM request. `OcrService` is the OCR exception here: it sends a multimodal Chat Completions request and is in scope, as listed above; OCR image preparation and local processing are not separate model calls. ASR and TTS endpoints remain outside this chat-account router. In particular, a tool call initiated by an assistant has an in-scope LLM decision request and a separate out-of-scope tool/service request. `ModelConfigPage`'s direct audio test is TTS, not an LLM test. No other direct production LLM endpoint call was found beyond `OcrService` and the chat provider boundary.
