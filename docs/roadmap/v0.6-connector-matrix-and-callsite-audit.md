# v0.6 M0: connector matrix and LLM call-site audit

This inventory freezes the CLIProxyAPI source at [`d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5`](https://github.com/router-for-me/CLIProxyAPI/tree/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5) (2026-10-09). It records built-in upstream authentication/execution code, not a promise that every account can use every model. Live login, request, and quota checks require provider credentials and platform access; this source review did not use credentials or make upstream requests.

## Connector boundary

The pinned [README](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/README.md), [auth-manager registration](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/cmd/auth_manager.go), [core executor registration](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/sdk/cliproxy/service_executors.go), and [example configuration](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/config.example.yaml) were cross-checked. The built-in login manager registers Codex, Claude, Antigravity, Kimi (three provider/domain IDs), xAI, Devin, and Meta authenticators. Core executors also implement Gemini API, Gemini Interactions, AI Studio relay, Vertex, and OpenAI-compatible upstreams.

The README mentions Gemini CLI among Google channels, but this snapshot has no Gemini CLI authenticator or `gemini-cli` provider executor. The core `gemini` executor is explicitly an API-key executor. The code-backed Google channels are `gemini`, `gemini-interactions`, `aistudio`, `vertex`, and `antigravity`; only Antigravity has a built-in Google user OAuth authenticator. Gemini CLI is therefore not counted as a separate account connector here. If it was intended to mean a distinct subscription login, this snapshot does not establish that implementation.

Likewise, API keys under `access.api-keys` authenticate clients to the proxy. They are not upstream credentials. The separate `api-keys` configuration section and the `openai-compatibility` groups are upstream credential/configuration paths.

### Catalogs, usage, and protocol distinction

Core model listings are assembled from provider catalogs and account/configured model mappings in [`service_models.go`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/sdk/cliproxy/service_models.go) and [`internal/registry`](https://github.com/router-for-me/CLIProxyAPI/tree/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/registry). Configured aliases, model exclusions, and provider settings can change the visible list. Codex and Devin model metadata have remote catalog refreshers; Antigravity has account capability probes. A listed model does not prove that a particular credential can use it.

Executors collect request-level usage when the upstream response provides it. This is not the same as remaining account quota. The inspected core code has distinct provider quota/balance signals for Codex, Antigravity, and Devin; for the other entries above, account balance/quota remains unknown unless an upstream response or error supplies a value. No credentials were used to validate those external reports.

Client-facing ingress formats and routes are separate from both the account matrix and each executor's native upstream request format. For conversation/model requests, CLIProxyAPI registers OpenAI Completions, Chat Completions and Responses; Gemini GenerateContent and Interactions; Anthropic Messages; and Codex-specific Responses aliases. It also registers OpenAI Realtime session/call endpoints at `/v1/realtime`. This is a scoped summary of conversation/model ingress, not a complete route catalog; image generation/editing, video, and audio/speech/TTS are separate media routes. The listed CLIProxyAPI ingress does not imply every executor supports every input or create upstream account connectors, and it does not expand Stroom's feature scope into a generic protocol gateway. Stroom's planned shared routing applies to the application model call paths audited below. Realtime is a protocol endpoint handled by `codexLiveHandler`, outside this Stroom unit's `ChatAdapter` chat/model-call scope. Antigravity is an upstream executor used through supported client formats, not a separate model-request route; its `/antigravity/callback` endpoint handles OAuth. See [`server_routes.go` OpenAI/Anthropic routes](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/api/server_routes.go#L71-L85), [`Gemini routes`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/api/server_routes.go#L127-L135), [`auxiliary media routes`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/api/server_routes.go#L73-L81), [`Realtime routes`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/api/server_routes.go#L92-L107), [`Codex route aliases`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/api/server_routes.go#L117-L124), [`Antigravity OAuth callback`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/api/server_routes.go#L180-L191), [`executor registration`](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/sdk/cliproxy/service_executors.go), and the [README overview](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/README.md).

## Stroom LLM call-site audit

The source audit searched production Dart under `lib/` for `ChatAdapter`, `ChatService`, `createChatProviderFromConfig`, `sendPrompt`, stream entry points, LLM endpoint/protocol strings, and HTTP client request calls, then followed each service construction and request path. At the audited base commit, `ChatAdapter` is the shared provider-resolution boundary for chat: it creates per-conversation or transient `ChatService` instances, and `createChatProviderFromConfig` selects the OpenAI-compatible or Anthropic provider. Those providers own the chat HTTP clients. `OcrService` separately sends image content to an OpenAI-compatible Chat Completions endpoint; despite being an OCR feature, that is a direct model request and is inventoried below.

### Explicit exclusions

OCR, ASR, TTS, MCP transport, HTTP tools, web search tools, file upload/download APIs, connectivity probes for MCP/HTTP tools, and other non-LLM service requests are outside this LLM router unless they make an LLM request. `OcrService` is the OCR exception here: it sends a multimodal Chat Completions request and is in scope, as listed above; OCR image preparation and local processing are not separate model calls. ASR and TTS endpoints remain outside this chat-account router. In particular, a tool call initiated by an assistant has an in-scope LLM decision request and a separate out-of-scope tool/service request. `ModelConfigPage`'s direct audio test is TTS, not an LLM test. No other direct production LLM endpoint call was found beyond `OcrService` and the chat provider boundary.
