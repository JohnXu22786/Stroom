# Stroom 0.6 Development Plan

`v0.6` is the development and integration branch for the owner-approved account, API, and subscription feature series. This plan defines the local account and model-group management work assigned to that version line. Track implementation units through reviewed pull requests into `v0.6`.

## Goal

Upgrade Stroom's LLM configuration into local account and model-group management, so a person can use API keys, custom compatible endpoints, and supported upstream OAuth, CLI, or subscription accounts with understandable usage limits and reliable routing between equivalent models.

## Scope

- Keep this a personal, local Stroom feature. Do not add multi-tenant accounts, a public relay or gateway, reseller billing, or generic client-protocol conversion.
- Replace the current LLM provider configuration workflow with separate upstream accounts, model mappings, and stable Stroom model groups. Keep the account and model configuration page separate from runtime request handling.
- Support API keys and custom compatible endpoints, along with every core upstream account/auth connector present in the frozen [CLIProxyAPI reference snapshot](https://github.com/router-for-me/CLIProxyAPI/tree/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5). The initial documented matrix includes OpenAI Codex OAuth, Anthropic Claude Code OAuth, Google Gemini CLI, Google Antigravity, Gemini API / Generative Language API keys, AI Studio Build, Vertex AI, xAI Grok Build OAuth, Moonshot Kimi OAuth/API, Meta Muse Code login/API key, Devin login, and configurable OpenAI-compatible upstreams. At M0, verify the snapshot's README, core auth/connectors code, and configuration docs; add any core connector found in code but omitted from this initial list to the frozen matrix. Third-party client integrations and peripheral projects are not upstream account connectors.
- Route shared LLM requests through the ChatAdapter/ChatService boundary. Audit all LLM call sites and bring in-scope direct calls under that shared routing path. OCR, ASR, TTS, MCP, and other non-LLM services remain outside this router.
- Preserve existing provider entries and stable model references during a validated, backed-up, retryable migration. Existing conversations, assistants, and internal tasks must continue resolving their saved model identities.
- Select accounts by model-group membership and priority tier. Use least-used selection by default within a tier; allow the agreed round-robin and balance preferences. Restrict fallback to either the same provider's account pool or the configured model group, according to its policy.
- Support account and optional group reserves, usage ceilings, five-hour/day/week/month windows, rolling windows by default with selectable calendar windows, concurrency caps, and observable route decisions. Use upstream-reported quota and usage when available; keep unknown values explicit and do not treat estimated price as an enforcement source.
- Store credentials in the platform secure-storage abstraction and keep only credential references in ordinary configuration. Do not expose secrets in logs or exports; describe platform limitations and unsupported storage behavior.
- Use the detailed [LLM account and model-group routing plan](../llm-account-routing-plan.md) as the agreed design and implementation acceptance reference.

## Milestones

These M0–M5 milestones are the repository's local roadmap and sequence the work. They are not GitHub milestone objects. After this documentation pull request merges, Batch may create a GitHub milestone linked to this plan to group the implementation issues and pull requests; this documentation unit does not create one.

### M0: Connector inventory and shared-call-site audit

- Pin the CLIProxyAPI source revision and audit its README, core auth/connectors code, and configuration documentation. Freeze a complete matrix of core upstream account connectors, authentication lifecycle, model discovery, request path, quota/usage reporting, and verifiable capabilities.
- Inventory Stroom's outgoing LLM call sites, including regular chat and transient title, compression, task, and assistant/tool requests. Identify any direct calls and record whether each belongs on the shared router.
- **Dependencies:** None.
- **Exit criteria:** A checked-in connector matrix records the exact reference commit and every core connector found in the snapshot; every in-scope Stroom LLM call site has an owner and routing disposition. No third-party client listing is counted as an upstream connector.

### M1: Account/model-group data, credential storage, and safe migration

- Define connector, account, upstream-model, stable model-group, credential-reference, quota/concurrency policy, and routing-state data.
- Implement platform-aware secure credential storage and migrate existing provider entries while preserving IDs and saved model references. Keep legacy reads available until migration and connector acceptance is complete.
- **Dependencies:** M0 connector and call-site inventory.
- **Exit criteria:** A repeatable migration can be validated and retried from a backup; migrated accounts retain their original models and credentials; existing conversations, assistants, and internal tasks still resolve their model identities; secrets remain outside ordinary configuration, logs, and exports.

### M2: API keys, custom endpoints, and core upstream connectors

- Implement the connector registry and account lifecycle, then API-key and custom compatible-endpoint accounts.
- Implement every core connector in the M0 frozen CLIProxyAPI matrix, including the authentication and request behavior required for each connector. Verify login or credential acceptance, refresh where applicable, model discovery, requests, and available quota/usage reporting per connector.
- **Dependencies:** M0 frozen matrix; M1 account/model-group schema and secure credential references.
- **Exit criteria:** Each frozen matrix row has a recorded implementation and per-capability verification result. Unsupported upstream capabilities and unavailable verification environments are called out accurately; no connector is counted complete merely because its settings can be saved.

### M3: Quota, usage, balance, concurrency, and fallback

- Add account and optional group reserves and usage ceilings, with fixed-value and percentage forms where a reliable total is known. Support five-hour/day/week/month rolling windows and selectable calendar windows, local-time resets, and account/group concurrency reservations.
- Implement priority tiers, least-used default selection, the agreed optional same-tier strategies, scoped fallback, retry classification, cooldowns, and explainable selected/skipped-account reasons. Do not replay after streamed output or a tool side effect.
- Prefer upstream-reported quota, reset, and usage data. Keep unknown balance explicit and use only observable local usage when an upstream has no reporting API.
- **Dependencies:** M1 account/group policy data; M2 connector capabilities and available upstream quota/usage sources.
- **Exit criteria:** Deterministic tests cover window boundaries, reserve/ceiling enforcement, concurrency release on success/error/timeout/cancel, priority and fallback scope, and retry safety. Route diagnostics explain each selected or skipped account without treating unknown quota as known capacity.

### M4: ChatAdapter integration and account/model-group UI

- Resolve stable model-group identities and apply account selection through ChatAdapter/ChatService for all in-scope regular and transient LLM calls.
- Replace the provider page's core forms with account and model-group workflows, including connection status, model capabilities, usage/quota, limits, concurrency, fallback settings, and actionable failure reasons.
- **Dependencies:** M1 data and migration; M2 connectors; M3 routing and usage policy.
- **Exit criteria:** The M0 call-site inventory confirms every in-scope LLM request uses the shared router; migrated conversation/assistant/internal-task model references still work; account and model-group settings expose the agreed controls and diagnostics without routing from UI widgets.

### M5: Regression, security, and release readiness

- Run focused migration, connector, routing, quota-window, concurrency, cancellation/retry, and UI regression acceptance across supported platforms.
- Review credential storage, logs/exports, OAuth refresh and disconnect behavior, fallback side effects, and honest capability reporting. Complete user documentation and connector limitation notes.
- **Dependencies:** M0–M4.
- **Exit criteria:** Existing configurations work after migration; the full frozen connector matrix has per-connector evidence; failed migrations can be recovered; requests are not replayed after output or side effects; supported-platform security and feature limitations are documented; required CI and release checks pass.

## Acceptance Criteria

- Existing provider configurations migrate without losing credentials, model mappings, or saved conversation, assistant, and internal-task model references.
- API-key and custom compatible endpoints work, and every core connector in the frozen CLIProxyAPI snapshot has an implementation and per-capability verification record.
- Regular and in-scope transient LLM requests use ChatAdapter/ChatService routing, while non-LLM services remain unaffected.
- Priority, same-tier selection, scoped fallback, reserve and ceiling rules, rolling/calendar windows, concurrency, cooldown, and safe retry behave as specified and can be diagnosed from the account/model-group UI.
- Credentials stay in secure storage; unsupported platform capabilities, unknown quota, and connector limitations are shown honestly.
- Focused regression, migration, connector, routing, security, and release-readiness checks pass before the v0.6 feature series is handed off for release.
