# Stroom 0.6 Development Plan

> **Status: Complete.** The v0.6 line brings account-based LLM configuration and model-group routing into Stroom's own Chat and Task Flow experiences. This plan describes the delivered scope; local automated checks do not certify every provider account, entitlement, device, or network environment.

## Goal

Let people manage upstream LLM accounts in Stroom, map stable Stroom model names to upstream models, and route Chat and Task Flow requests according to explicit account and model-group policies.

## Scope

- Keep account credentials and routing local to Stroom. Do not add an external API gateway or listener.
- Provide account setup, editing, reconnection, pause, deletion, model discovery, connection diagnostics, capability display, quota/usage reporting, and concurrency controls where the upstream exposes the information.
- Treat authentication and request protocol as separate settings. Use each provider's native API where appropriate, with per-model protocol overrides when supported.
- Store conversations in Stroom's common conversation format, preserving text, tool activity, protocol extensions, and supported media across account changes.
- Map stable Stroom model IDs to one or more account/model pairs. Apply priority, least-used, round-robin, known-balance preference, quota, concurrency, and configured fallback-scope policies.
- Keep local conversation history and attachments when account routing changes. A successful account may be preferred for the same conversation for up to one hour. Fallback stays within the configured group or account scope.
- Preserve upstream reasoning content only when the provider returns it in a representable protocol field. Hidden provider state and private caches are not transferable.
- Keep unsupported authentication and media capabilities explicit. Do not infer a working chat route from a connector entry or a credential that can be saved.

## Delivered areas

- Account and model-group storage, secure credential references, migration, and management UI.
- Provider-specific authentication, model discovery, request adapters, and protocol bridges for supported conversational routes.
- Shared Chat and Task Flow routing, usage and quota policies, concurrency limits, scoped fallback, and request diagnostics.
- Local conversation history, attachment, tool-call, and multimodal handling through the common Stroom conversation model.
- Regression coverage for account lifecycle, connector routes, protocol conversion, routing decisions, persistence, and affected UI flows.

## Acceptance

A connector is available for Chat or Task Flow only when its authentication, request route, and advertised model capabilities are implemented for that path. Unknown quota remains unknown. Unsupported upstream routes stay unavailable. Local automated checks and provider-specific limitations are documented with the relevant user-facing account guidance.
